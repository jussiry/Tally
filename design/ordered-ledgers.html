Should ledgers be ordered?

A thinking piece, not a TIP: it lays out the options for giving the records between two friends an agreed order, so a later TIP can pick one. Started 2026-11-04.

Where we are

Each user keeps one ledger of every record they sent or received. The records between two friends are its bilateral slice, which is what sync exchanges. The slice is an unordered set: entries are sorted by the local, unsigned timestamp, and sync merges by entry id.

That is enough for records whose effect does not depend on order. Transactions add up the same in any order, and a payment request is closed by a set lookup, so a cancel that arrives before its request still works.

Where order matters

  • Latest-wins values — a name change, a trust-limit change, notification preferences. Two changes made close together are applied in arrival order, so two devices can end up with different "latest" values.
  • State changes of the friendship — accept, default, reactivation. Records written while a friend was offline may describe a relationship that has since changed.
  • Crossing records — a cancel crossing a payment for the same request. Today both are kept and the user is told; nothing decides which came first.
  • Conditional records — anything valid only against a known state, such as a future offer to exchange one currency for another at a fixed rate. Without an order, "the state when this was signed" cannot be stated.
  • Completeness — with a set, a device cannot tell "we are in sync" from "a record never arrived". Recovery from a friend proves each record is genuine, not that none are missing.

Whether the ledger is stored per user or per connection is a separate question. Order is about the bilateral slice either way; storing per connection mostly makes that slice easier to sync, checkpoint and delete as a unit.

Options

1. Keep the set; make the rules order-free

Leave the ledger unordered and design every record type so its effect is the same in any order: a set lookup for closures, and a fixed tie-break for latest-wins values.

  • For: no change to sync or storage; nothing ever waits for a missing record.
  • Against: each new record type needs its own rule, and some cannot have one (conditional records). No proof of completeness.

2. Order by signed time

Order by originated_at, which the author signs, instead of the local timestamp, with a fixed tie-break.

  • For: cheap; both sides compute the same order from the same records.
  • Against: clocks are wrong and can be set back, so "latest" is whatever the author claims. A late-arriving record can still land in the middle of history. No proof of completeness.

3. One shared hash chain per connection

Every record names the hash of the previous record between the two friends. Both friends hold the same chain, and its latest hash stands for the whole history.

  • For: one total order, so "the next record between us" means one thing. Comparing latest hashes shows at once whether two devices agree, and a gap shows which record is missing. Earlier records can't be dropped without breaking the chain. Fits TIP-8: a checkpoint becomes a co-signed latest hash.
  • Against: offline use means both friends, or two devices of one friend, will sometimes add a record after the same hash. These forks have to be merged (below). A record is only final once the friend has built on it. One missing record holds up the ones after it.

4. Two author chains per connection

Each friend chains only their own records (prev), and each record also names the latest record seen from the other friend (seen). Both friends still hold both chains.

  • For: the two friends can't fork each other, so records are final as soon as they're written. Still proves completeness per author.
  • Against: only a partial order: two records written at the same moment have no "first". Rules have to be phrased per author ("valid while its author hasn't written since"), which is less natural than one order. Devices of one user can still fork their own chain.

5. Checkpoints only

Keep the set, and let TIP-8 checkpoints fix the agreed state from time to time.

  • For: already planned; bounds how far two devices can disagree.
  • Against: order is only known at checkpoints; between them the questions above remain.

Merging forks automatically (option 3)

Tally rests on agreements between two parties, and both parties may rewrite what they both agree on. So a fork is not damage, just two records competing for the same place, and a rule both clients apply settles it with no user involvement:

  1. A fixed rule picks the winner, for example the record with the lower hash.
  2. The loser's author re-signs it after the winner. Their client does this on its own, the next time it is online.
  3. Before re-signing, the client checks the record against the new state. If it no longer holds (a trust limit now exceeded, a condition no longer met), the record is dropped and the user is told what happened, not asked.

Things to keep in mind:

  • Pending state. A record not yet built on by the friend may still move or be dropped. The UI, and OS notifications, should treat it as pending.
  • Only the author can re-sign. A losing record waits for its author's device. With an external signer (TIP-6) a re-sign may raise a prompt.
  • References by hash change. Records that refer to others should keep using ids, which survive a re-sign, and use hashes only for the chain itself.
  • Records involving several friends (TIP-2, TIP-7) touch several chains, and a fork in one can drop that part. Their all-or-nothing rule then has to see the drop.

Leaning

Option 3 with automatic merging gives the simplest rules to write against: one order, a quick in-sync check, and no user decisions. Its cost is the pending state and the merge machinery. Option 4 is the fallback if waiting for the friend to build on a record turns out to hurt too much offline. Either way the move fits together with TIP-8, which can provide the starting point of each chain for existing history.

Open questions

  1. Which record types belong in the chain? Probably anything that affects the balance or the relationship; not transport traffic (sync, receipts) or records only for one's own devices.
  2. The fork rule: lower hash, or something that favours, say, the earlier signed time?
  3. How a user's own devices take part: one chain position shared through self-sync, or forks between devices treated like any other fork.
  4. Migration: start each chain from a TIP-8 checkpoint of the existing history, or from the existing records in timestamp order?
